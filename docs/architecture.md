# Architecture

## Current application

The application uses the Flask factory in `app/__init__.py` to register web blueprints. Routes render templates and pass them the results of plain-Python service functions. The business logic does not depend on Flask, a database, a browser, or live third-party services.

| Responsibility | Current location | Notes |
| --- | --- | --- |
| HTTP routes | `app/routes/` | Health, dashboard, synthetic scenario pages, the guided walkthrough at `/walkthrough`, the control-mapping library at `/mappings`, and the JSON intake API under `/api/v1`. |
| Business logic | `app/services/` | Risk evaluation, the single org-policy check, evidence validation, control mapping, scenario orchestration, the walkthrough stop list, local workflow persistence, human decisions, observed workflow metrics, cost calculations, the reviewer package, file import, the optional trust-center GET, and the bot intake contract. |
| Database | `app/db.py`, `app/schema.sql` | SQLite schema and request-scoped connections for risks, remediation actions, human decisions, reviewer-authored findings, workflow events, and browser sandboxes. `DATABASE_PATH` can place the file on a persistent host volume. Startup adds policy columns to a risk table created before those columns existed. Startup also adds `prev_hash`, `hash`, and `chain_origin` on `workflow_events` when those columns are missing, hashes rows that already exist once, and marks those rows `chained_after_the_fact`. Later events are hashed when they are inserted. `verify_event_chain()` checks one chain without Flask. The methods page and the dashboard show every chain. The label is tamper-evident, not tamper-proof. A browser sandbox is a separate chain from the shared chain. `GET /health` opens that file read-only and reports whether its catalog can be read. It does not check the hash chain and it does not write a sandbox. |
| Versioned rules/data | `app/data/` | Risk rules, the single org policy profile, the public intake questionnaire, evidence freshness policy, mappings, and fixed-date demo scenarios. |
| Presentation | `app/templates/`, `app/static/` | Server-rendered HTML and responsive CSS. |
| Automated checks | `tests/` | pytest tests include service-level business logic and Flask route behavior. |
| Documentation | `docs/` | Design, assumptions, and limitations. |

`app/services/intake_importer.py` turns a CSV, `.xlsx`, or simulated ServiceNow JSON/CSV file into the same form dictionary the public intake page posts. `openpyxl` reads workbooks. CSV and JSON stay in the standard library. The preview does not call the risk engine. After confirmation, `build_intake` and `run_intake` do. Confirm does not insert a risk row. A separate save posts the same confirmation for one row and calls `register_intake`. Ticket fields such as priority are returned as context and are not scored. Optional `vendor_direction`, `residual_direction`, and `direction_note` columns are intake context for a person. They are not scored. See `docs/import-formats.md`.

`app/services/sample_register.py` copies three synthetic scenarios into the caller's sandbox when that browser has no saved risks and the visitor posts Load sample data. The post is same-origin only. A missing sandbox id is refused, so the shared register is not written. The insert goes through `register_scenario`, which appends that sandbox's hash chain. A second post does not insert duplicates. The set is refused when it would pass `SANDBOX_MAX_RISKS`. Those rows are observed register rows under definition 9. They are not inputs to `calculate_cost()`.

`app/services/result_explain.py` also builds the plain-language summary and the one-line reason when a tier is withheld. Both restate the engine result. They do not rescore it. Rule codes stay in the Technical detail disclosure.

`app/services/bot_intake.py` accepts that same form as a JSON object, or a file the importer already parses. `app/cli.py` (`python -m app.cli`) and `app/routes/api.py` return the document it builds from `run_intake`. The residual tier, factor list, escalation records, and rule-set version are copied from the risk engine. Those callers insert a risk row only when persist is requested and the human disposition passes the same checks as a decision on a saved scenario. See `docs/bot-contract.md`.

A requested trust-center fetch performs one outbound HTTP GET. File import does not fetch. Tests stub the opener and the resolver, and they do not use the public network. Each hop resolves the hostname once, checks every returned address, and opens TCP only to an address from that check. The check refuses private, loopback, link-local, multicast, reserved, unspecified, and other non-global addresses, including IPv4-mapped forms of those ranges and the metadata address 169.254.169.254. One blocked address in the set refuses the hop. The HTTP Host header is the original hostname. For HTTPS, TLS SNI and certificate verification use that same hostname. A redirect is resolved and pinned again, up to the existing redirect limit. Environment proxies are not used. The pin stops a DNS change between the check and the connection. It is not a full egress sandbox: a public address can still belong to an unexpected host, and a host route or transparent proxy can still move packets. A host-level egress firewall is still recommended.

The scenario runner composes evidence validation, risk evaluation, and mapping in that order. It passes the derived claim evidence results into the risk engine and mapping service. The same validation call checks required contract clauses and passes those statuses through. A missing or conflicting status is never replaced by a UI-generated conclusion. Scenario data is loaded from version-controlled JSON and evaluated on an explicit fixed date. Risk evaluation also reads `app/data/org_policy.json` and attaches that policy's id, version, outcome, and the evidence status of each required contract clause. A user can save a synthetic scenario result to SQLite; the persistence service stores the risk rationale and references, creates a follow-up action for escalations, a matched hard restriction, or evidence gaps, and records local workflow events using parameterized SQL. Each new event stores `prev_hash` and `hash`. The hash is SHA-256 of canonical JSON of the event fields plus `prev_hash`, including `chain_origin`. Events with no sandbox id are one shared chain in `event_id` order. Each browser sandbox is a separate chain in `event_id` order. `verify_event_chain()` checks one chain. The sandbox id is stored on the row and is not part of the hashed JSON. Deleting a stale sandbox removes that chain and does not rewrite the others. `appended` means the row was hashed when it was written. `chained_after_the_fact` means startup hashed a row that already existed. That backfill runs once. A later edit is not given a new hash.

A saved risk can then store one human decision: approve, approve with conditions, escalate, or reject. The same row can store optional `handling_minutes`, optional `rework_minutes`, optional `manual_touches`, optional `handoffs`, optional `authenticated_effort_minutes`, and optional `cash_savings_dollars`. The first four are self-reported whole numbers. Authenticated effort minutes and cash savings dollars are stored only when a signed-in reviewer entered them. Null means unmeasured. Cash savings dollars are not a wage times the other numbers. Rework minutes are time spent redoing work after a first pass. They are not handling minutes. Manual touches are a count of human touchpoints on that assessment. They are not handling minutes and not rework minutes. Handoffs are a count of times the assessment was handed between people or queues before disposition. They are not handling minutes, not rework minutes, and not manual touches. The workflow service copies the policy reference and rule set version from the saved assessment, requires an exception rationale before an approval of a prohibited result, and writes a `decision_recorded` event. Escalate is a person's choice to send the case on. It is not an approval and it does not require an exception rationale. Replacing a decision updates that row and writes another event. The prohibited outcome on the assessment is not edited. See `docs/risk-model.md` for why an exception is allowed. General intake uses the same insert, then writes the decision in that same transaction. The intake's scenario id is `intake-` plus a random suffix so the scenario unique key still holds. That save writes `intake_received` before `risk_created`, then `decision_recorded`. A scenario save writes `risk_created` and does not write `intake_received`.

`app/services/workflow_metrics.py` reads those rows. It counts assessments, open remediation, residual tiers, claim evidence, clause evidence, and current dispositions. Cycle time is the elapsed seconds from the earliest `intake_received` timestamp to the earliest `decision_recorded` timestamp on the same risk. Self-reported handling time is the median of `handling_minutes` on current decision rows that have a number. Self-reported rework time is the median of `rework_minutes` on those rows, calculated separately. Self-reported manual touches are the median of `manual_touches` on those rows, calculated separately. Self-reported handoffs are the median of `handoffs` on those rows, calculated separately. Authenticated effort is the median of `authenticated_effort_minutes` on those rows, calculated separately. Cash savings are the median of `cash_savings_dollars` on those rows, calculated separately. A row with no number stays out of that median. The monthly assessment rate is the count of current `decided_at` timestamps in the closed 30-day window ending at the latest readable timestamp, and only when the earliest readable timestamp is at least 30 days earlier. Otherwise that card says Not measured. The function does not write, and it does not call `calculate_cost()`. The dashboard and the methods page pass this browser's sandbox id. The count then includes that sandbox and any row whose sandbox id is null. Another browser's sandbox is not included. Definition 9 is unchanged. A direct call that omits the scope still reads the whole table. An empty scope still says Not measured where a figure was not recorded. It reads `avoided_incident_value()` only to decide whether that modeled figure stays on the unmeasured list. Register rows are not inputs to it. The dashboard and the methods page pass `calculate_cost()`, `avoided_incident_value()`, and `observed_metrics()` to the templates as separate values. See `docs/cost-model.md`.

## Current limitations

Scenario runs are deterministic examples, not vendor records. File import on `/try/import` previews synthetic rows and assesses them on confirm. The ServiceNow shape is not a live integration. A row is stored only after a separate save. The bot contract returns one assessment or a file batch. It stores them only when persist is true and a person supplies a disposition. A reviewer can write a finding on a saved assessment: title, description, severity, one or more mappings from the current mapping set, an optional vendor label, the assessment itself as the linked risk, an owner, and a status of open or closed. Closing stores a closing note. The finding is labeled reviewer-authored and is stored in the caller's sandbox. Engine escalations stay on the assessment and are labeled separately. The finding does not change the inherent score, the residual tier, evidence confidence, or the policy outcome. Draft mappings stay draft. This is not a general case-management system. Observed metrics cover the saved register only: volume, open remediation, distributions, disposition counts, elapsed intake-to-disposition time, optional self-reported handling minutes, optional self-reported rework minutes, optional self-reported manual touches, optional self-reported handoffs, and a monthly assessment rate from current decision timestamps when those timestamps cover at least 30 days. A shorter history leaves the rate Not measured. Authenticated effort is that separate optional minute count, shown only when a signed-in reviewer stored it, and Not measured otherwise. Cash savings are that separate optional dollar count, shown only when a signed-in reviewer stored it, and Not measured otherwise. They are not produced by the cost formula. Avoided-incident value is a separate modeled-assumption card. The shipped assumptions leave `incident_cost` and `avoided_incident_count` null, so that card says Not measured. It is not an observed register figure and it is not produced by the cost formula. The cost panel remains the illustrative formula. The optional HTTP Basic gate can require a shared password when `REQUIRE_AUTH` is enabled. The hosted demo leaves it off. A browser save from the demo register action, an import save, or `POST /api/v1/intake/assess` with `persist: true` writes into that browser's sandbox. The sandbox is a random id in a signed `grc_sandbox` cookie (`HttpOnly`, `SameSite=Lax`). It is not a login, not a user account, and not multi-tenancy. Anyone who holds the cookie can read that sandbox. Clearing cookies drops the link. `/try/assess` and import confirm still write nothing. The seeded scenario pages stay visible to every visitor and are read-only examples. A save copies one into the sandbox. Rows with a null sandbox id, including the local CLI and rows saved before sandboxes existed, stay visible to every visitor. A sandbox holds at most `SANDBOX_MAX_RISKS` saved assessments (default 25). A sandbox not seen for `SANDBOX_TTL_SECONDS` (default 14 days) is deleted, including its event chain. The cookie is signed with `SECRET_KEY`, or with `instance/sandbox_secret` when that variable is unset. It is not an identity system or production access-control design. The workflow log is tamper-evident. Someone with access to the database can still rewrite the whole chain, so it is not tamper-proof, immutable storage, a production audit log, or a certification. The local Flask development server must not be exposed publicly. A trust-center fetch collects a public page for review. It is not independent verification. DNS pinning keeps each connection on an address that was checked for that hop, with the certificate checked against the original hostname. That pin is not a complete SSRF sandbox. A host-level egress firewall is still recommended.

## What production use would still require

A reviewer should expect the gaps below. The application stays an illustrative portfolio prototype.

- A decider identity. The optional password is one shared demo gate. It is not per-person authentication, and the hosted demo leaves it off. The name typed into the form is not checked against a directory.
- A register bound to a person. The public demo keeps each browser's opt-in saves in a cookie sandbox. That cookie is not a login. Anyone holding it can read that sandbox, and clearing it drops the link. Rows with no sandbox id stay visible to every visitor.
- An event log that a person with database access cannot rebuild. The local log is tamper-evident. It is not tamper-proof, immutable storage, a production audit log, or a certification.
- Authoritative review of the draft ISO/IEC 27001 and ISO/IEC 42001 mappings before anyone treats them as reviewed. A mapping is not conformity.
- A live workflow system, if one is required. ServiceNow here is a file shape and a mock ticket. Nothing is sent.
- Off-box backups and a repeated snapshot restore drill. One drill, on 2026-10-27, is recorded in `docs/deployment.md`. It covers the snapshot used that day. A later snapshot is untested until another drill is recorded.
- An observed avoided-incident value. The shipped assumptions leave `incident_cost` and `avoided_incident_count` null, so the card says Not measured. A later product of those two assumptions would still be a labeled model, not an observed register figure, not cash savings, and not the labor-capacity example.
- More than one host. SQLite on this single instance is the demo design. It is not a highly available database.

## Design choices

- Standard-library JSON, CSV, and SQLite are preferred for the prototype. `openpyxl` is the one added library, and it only reads `.xlsx` workbooks.
- Flask remains at the route and presentation boundary; core functions can be tested directly.
- Static JSON makes every demonstration input inspectable and repeatable.
- Mapping results retain source, version, claim, and evidence references while remaining visibly draft. `/mappings` lists the whole library from `list_library`. Mapping set 0.2.0 includes draft ISO/IEC 27001 and ISO/IEC 42001 review prompts beside the NIST entries. A shared claim topic is the join. It is not cross-framework equivalence.
- No external AI service participates in scoring or approval decisions.
- One org policy file is enough. There is no tenant selector.
- The policy outcome is calculated in the risk engine. Templates display it. They do not decide it.
- `app/services/result_explain.py` turns that result into reviewer sentences: why a rule fired, and what a claim, clause, or mapping means for the decision. It does not change scores, tiers, or evidence statuses. `app/services/intake_replay.py` copies answers back onto the public form. A re-run still goes through intake and the risk engine. Fetch stays no unless the visitor chooses it again. An unsaved `/try/` run is not a register disposition.
- `GET /health` reports SQLite reachability. The check is a read-only open and a catalog read. It does not rate the data, the schema, or the host.
- Required contract clauses are data in the org policy. The evidence validator derives each clause status. The risk engine records that status and does not score it. A gap does not block the human decision.
- A prohibited result can be approved only with an exception rationale because a person, not the score, makes the disposition. The restriction stays on the record. There is no configured non-overridable ban.
- The decider is a name or role typed into the form. Nothing checks it against a directory or against the restriction's owner role.
- The public intake questionnaire is versioned data. It chooses prompts and which trust-center citation becomes an evidence record. Questionnaire 1.1.0 also asks for vendor direction, residual direction, and an optional note. Those answers are stored beside the result for a person. The risk engine does not read them. The residual formula is unchanged. The risk engine still scores. A trust-center URL is stored as a citation unless the form sets `fetch_trust_center` to yes. That choice performs one HTTP GET in `app/services/trust_center_fetch.py`, pinned to the addresses checked for that hop, and stores an excerpt for review. The evidence validator marks the fetch `not_reviewed`. It is not a scored claim and it does not approve the vendor. File import does not fetch. The reviewer package is JSON and plain text built from the assessment result. It does not approve the vendor.
- File import reuses that questionnaire. A spreadsheet column and a ServiceNow `u_` field are two ways to fill in the same form. The importer does not keep a second scoring model.
- The bot contract is a third way to submit that form. `app/cli.py` and `/api/v1/intake/assess` call `build_intake` and `run_intake`. They do not keep a second scoring model, and they do not approve the vendor.
- Observed metrics are counted from persisted rows and event timestamps. The cost service keeps its own assumption file. The pages render both results and do not copy one into the other. The event-chain check is a third result. It does not change definition 9 and it does not call `calculate_cost()`.
- A reviewer-authored finding is a row on one saved assessment. `app/services/findings.py` validates it and writes `finding_created`, `finding_updated`, or `finding_closed` through the same hash chain as other workflow events. The risk engine does not read the row. Inherent score, residual tier, evidence confidence, and the policy outcome stay as the engine left them. Linked mapping text and review status are read from the mapping set when the finding is shown. A draft entry stays draft. The optional vendor label can be blank. The linked risk is the saved assessment the finding was written on. The row carries the caller's sandbox id, including when that assessment is a shared row. Another sandbox does not receive the finding or its event. A sandbox holds at most `SANDBOX_MAX_FINDINGS` findings. The default is 50. Observed metrics stay on definition 9. The finding is not an input to `calculate_cost()`.
- The workflow-event hash chain is a local trace. The methods page and the dashboard show `verify_event_chain()` on every chain. Events with no sandbox id are the shared chain. Each browser sandbox is its own chain. An empty log checks as intact. Deleting every row and the stored tip also checks as intact. Deleting one stale sandbox removes that chain only. A person who rewrites the rows and the hashes produces a chain that checks as intact. Rows hashed during the one-time startup backfill stay marked chained after the fact. The chain check is not an observed metric and it does not call `calculate_cost()`. The event count on that panel can include other sandboxes. The pages do not list those events.
- `/walkthrough` lists thirteen stops and links to the existing pages with a `walk` query. The stops include a custom vendor and the optional trust-center choice on `/try/`, the conflicting-permissions scenario, and `/try/import`. A guided assessment keeps that note on the result, including a successful submit from the intake stop. On the intake, custom-vendor, and trust-center stops, Next is withheld until that submit succeeds. A validation error stays on the stop and still withholds Next. The cookie records the stop id only, so the form holds Next again on a later visit. File import withholds Next until confirm renders the assessment. A preview, a rejected file, and a later visit to the upload form still withhold it. A failed save on that result still offers Next, because confirm already ran the engine. The decision stop withholds Next until the eligibility risk has a recorded decision. A rejected decision stays on that risk and still withholds Next. Opening the decision page again shows Next, because the decision is stored on the record. The save stop withholds Next until the register action, through the same `await_submission` rule. Ready-made scenario cards on a stop that is waiting keep that stop's `walk` query, so opening one does not advance Next. Cards on a guided page that is not waiting use the stop for that scenario: the try-page stop, or the save stop for the eligibility case on the demo surface. `/try/` and `/demo/` without `walk` stay coach-free. Fetch stays optional: no does not open the URL, and yes stores an excerpt for review that is not verified evidence and does not approve the vendor. Preview and confirm keep the import note. A guided import save opens the next stop. The coaching note is rendered only when that query names a known stop. Progress is the `walk_step` cookie, a step id kept for 12 hours. The guide does not calculate a score and does not insert a risk. Saving still uses the demo register action, and that action moves the guide from the save stop to the decision stop. Pages without the query are unchanged. When `REQUIRE_AUTH` is enabled, `/walkthrough` and the later stops use the same gate as the dashboard. The `/try/` stops stay open with the rest of the public demo. The hosted demo leaves the gate off.
